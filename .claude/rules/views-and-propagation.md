# Views and incremental propagation

- Views use `Rc<RefCell<>>` for shared source access, with their own derived state
- View parents are `Rc<RefCell<dyn ReadableTable>>`. Tables and synchronized filters/sorts/aggregates/joins expose changesets in their own row coordinates; children of projection/computed views use version-checked full refresh. A view's `version()` includes its parents for staleness/iterator guards and is independent of its output changeset sequence. Always sync parents before children (tick registration order is topological).
- Consumer cursors belong to their immediate parent's stream. Use `root_changeset_cursor()` / `root_changeset_cursors()` for tick compaction; they return `usize::MAX` for derived sources. Never compare a filter's output cursor with a root table's cursor. A consumer created while a filter is stale has no coherent baseline and must refresh after the parent syncs.
- `filter_changes.rs` shares replay and output emission between native/Python filters. It reconstructs historical updated rows across later shifts/deletes and emits filter-coordinate events. Batches up to 256 changes replay; larger batches rebuild. One successful non-empty input batch is retained; a no-op sync preserves history, and rebuild uses `Changeset::invalidate()` to force even caught-up consumers to refresh. Python callbacks are evaluated before committing indices/history, so errors are retryable. See `docs/INCREMENTAL_FILTER_PIPELINE.md` and `impl/tests/filter_pipeline.rs`.
- Aggregate group-key updates use the same historical-row reconstruction. MIN/MAX keep each group's values in an ordered multiset (`f64::total_cmp`, so -0.0 < 0.0), so removing an extreme never rescans the source; percentile columns keep their sorted `Vec`. Removed values come from changeset payloads and must match a held value exactly (debug-asserted).
- SortedView caches only sort keys in parent coordinates plus forward/inverse index mappings. Small batches (up to 256 input events) replay against historical keys, never live-parent comparisons. A moved row emits delete(old full row) + insert(new full row); stationary edits emit CellUpdated. Ties follow parent order, NaNs sort after numbers ascending (before descending), and signed zero ties are stable. History/invalidation follow the filter contract. See `docs/INCREMENTAL_SORTED_PIPELINE.md`.
- Aggregate rows map to groups through `row_groups`, a vector indexed by parent position (`None` for a row in no group); each group keeps a row count and a shared `Rc<GroupKey>`. Never key per-row state by position in a hash: every structural event would rehash it (about 90 ms at 1M rows before 2026-10-26). Events apply in changeset order: an insert or delete shifts `row_groups` with one memmove, a group-key update overwrites its entry in place, and an out-of-range event index rebuilds before any state changes. Batches with multiple structural events over 512 total events rebuild. Emptied groups keep their `group_order` slot until batch end (`compact_group_order`); never shift/renumber the tail per removal (O(k·groups)).
- AggregateView publishes history in group coordinates (`group_order` positions, kept in `GroupState::position`). Each incremental batch is a net diff: removing a pre-batch group emits `RowDeleted` with its full pre-batch row; at batch end, surviving groups emit `CellUpdated` only for changed result columns (floats compared by bits) and new groups emit tail `RowInserted`s. New groups only append, so pre-batch positions stay valid for consumers mid-batch. An empty input batch must record the parent version, or an excluded upstream edit hides history. Otherwise history/invalidation follow the filter contract. See `impl/tests/aggregate_pipeline.rs`.
- Join construction/refresh costs O(N+M+R), where R is output size. Rust joins replay table/filter/sort/aggregate/join history when available; parents without output history require version-checked rebuilds. JoinView publishes history in join coordinates (`join_index` positions, `right_`-prefixed right columns): one event per index mutation (placeholder fills are `CellUpdated` from Null), non-key updates fanned out to every output row of the parent row, and the value-only side applied first so the structural side reads the other parent live. Key updates rebuild before/after rows with `row_after_update`. Batches over 512 output events invalidate; rebuilds (both sides structural, key update before a shift, unreadable rows) invalidate. `sync()` returns true for value-only edits. Matches for inserts and key updates come from the other side's `*_key_hashes` vector (one per side, built lazily from the live parent, maintained per structural event in changeset order, dropped by rebuilds): one scan per sync for every target key, each candidate verified against its live key. Read a side's vector only when that side has no structural changes in the sync; with a structural left and a value-only right, the right pass runs first against pre-batch `join_index`, so a live left would be wrong. Value-only right batches locate their entries with one targeted pass over `join_index` (`right_targets_positions`). Out-of-range event indices rebuild before any state changes. See `impl/tests/join_pipeline.rs`. Float join keys fold -0.0 into +0.0 (like sorting/grouping); NaN keys never match.
- Iterator mutation guards: table/filter/projection/computed iterators capture the root table version; join/sort/aggregate iterators use `ReadableTable::version()` including ancestors and their own sync counter. All detect root mutations; the latter also detect view-version advances on sync/refresh. Filter-only refresh without root mutation is not detected. No-op sync does not invalidate an iterator.
- JoinView registers with both parent tables for tick() propagation via JoinLeft/JoinRight variants
